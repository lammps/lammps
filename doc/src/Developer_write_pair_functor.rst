Writing a pair style with the FUNCTOR framework
===============================================

The :ref:`FUNCTOR <PKG-FUNCTOR>` package provides a template-based framework for
implementing *simple, pairwise-additive* pair styles with much less boilerplate
than a stand-alone :doc:`Pair <Modify_pair>` subclass, while automatically
applying three performance optimizations adopted from the OPT and OPENMP
packages:

#. the per-atom position and force arrays are accessed as a contiguous
   *array of structs* so the compiler can vectorize and cache them;
#. the force on the outer-loop atom is accumulated in local variables and
   written back to the global array only once per atom;
#. the inner loop is compiled separately for each combination of the
   energy/virial, energy, Newton, and Coulomb-table flags, so those branches
   disappear from the hot path.

You write only a small **evaluator** struct that describes the functional form
of one interaction.  A shared **driver** template (``PairFunctor``) supplies the
neighbor loop, parameter storage, mixing, restart I/O, and the optimizations; a
compile-time **Coulomb policy** supplies the electrostatics.  This guide
explains the evaluator contract and walks through adding a new style.

When *not* to use this framework
--------------------------------

The framework is only for short-range, two-body, pairwise-additive potentials
whose energy depends on a single pair distance.  Do **not** use it for many-body
potentials (EAM, Tersoff, ReaxFF, ...), fully tabulated potentials, or styles
that need a second neighbor list.  Those should remain regular ``Pair``
subclasses.

Anatomy of a FUNCTOR pair style
-------------------------------

A complete style is three pieces:

#. an **evaluator** struct (the only physics you write), placed in its own
   header (e.g. ``evaluator_lj_cut.h``) that includes the shared
   ``functor_evaluator.h``;
#. a **Coulomb policy** chosen from ``functor_coul_policies.h`` -- you select
   one, you do not normally write one;
#. a **thin registered class** (``pair_<name>_functor.h`` / ``.cpp``) that binds
   the evaluator and policy together and exposes the style name to LAMMPS.

The evaluator contract
----------------------

An evaluator is a struct with no virtual functions; every method is ``static``
and ``inline`` so it inlines into the driver's templated inner loop.  It must
define:

* ``struct Coeff`` -- the *raw* per-type-pair coefficients exactly as typed on
  the ``pair_coeff`` line (e.g. ``epsilon``, ``sigma``, ``cut``).  Used for
  mixing and restart files.  It must contain a ``double cut;`` member.
* ``struct Param`` -- the *derived* quantities used in the hot loop (e.g. the
  precomputed ``lj1..lj4`` and ``offset``).  It must contain a
  ``double cutsq;`` member, which the driver uses as the per-pair cutoff test.
  Declare it ``struct alignas(64) Param`` so that each entry of the driver's
  flat parameter matrix occupies its own cache line (worth ~1-2% for systems
  with several atom types).
* ``static constexpr bool needs_charge`` -- ``true`` if the evaluator itself
  reads per-atom charge (most do not; Coulomb is handled by the policy).
* ``static constexpr bool has_mixing`` -- ``true`` if off-diagonal type pairs
  may be generated by mixing.  When ``false`` (e.g. Morse), the driver requires
  every pair to be set explicitly.
* ``static constexpr bool has_vdw`` -- ``true`` for a real van der Waals
  potential; ``false`` for the placeholder zero evaluator used by pure-Coulomb
  styles.  It tells the driver whether the leading ``pair_style`` cutoff
  argument is a van der Waals cutoff or belongs to the Coulomb policy.
* ``struct Global`` -- style-global parameters that are not per-type-pair (e.g.
  the inner/outer switching cutoffs of CHARMM).  Empty (``struct Global {};``)
  for most potentials.  The driver holds one instance, fills it in ``settings``,
  passes it to ``derive``, and persists it across restarts.
* ``static int settings(int narg, char **arg, LAMMPS *lmp, double &cut_global,
  Global &g)`` -- parse the leading van der Waals cutoff argument(s) and any
  global parameters from the ``pair_style`` line; set ``cut_global`` (the vdW
  cutoff used as the per-pair default) and return the number of arguments
  consumed.  The driver parses any trailing Coulomb cutoff itself.
* ``static Coeff parse(int narg, char **arg, LAMMPS *lmp, double cut_global,
  int &nconsumed)`` -- parse one ``pair_coeff`` argument list into a ``Coeff``
  (``arg[0]``/``arg[1]`` are the type ranges; numeric coefficients start at
  ``arg[2]``).  Set ``nconsumed`` to the number of arguments consumed starting
  at ``arg[2]`` so the driver knows where an optional Coulomb-cutoff argument
  begins; do not reject trailing arguments (the driver enforces the upper bound,
  which depends on the Coulomb policy).
* ``static Coeff mix(const Coeff &i, const Coeff &j, Pair *p)`` -- combine
  diagonal coefficients for an unset off-diagonal pair (only required when
  ``has_mixing`` is true).  ``Pair::mix_energy`` and ``Pair::mix_distance`` are
  public and may be called through ``p``.
* ``static Param derive(const Coeff &c, int offset_flag, const Global &g)`` --
  precompute the ``Param`` (and energy offset) from a ``Coeff`` (and the global
  parameters ``g``); also set ``Param::cutsq``.
* ``template <bool EFLAG> static PairContribution pair(double rsq, const Param
  &p, double factor_lj)`` -- **the hot path**.  Return ``{fpair, energy}`` where
  ``fpair`` is the scalar force divided by *r* and ``energy`` is the pair energy
  (computed only when the ``EFLAG`` template parameter is true, so the energy
  term is dropped from the force-only code path at compile time).  Apply
  ``factor_lj`` (the special-bonds scale) to both.  The driver has already
  checked ``rsq < p.cutsq``.  ``PairContribution`` is defined in
  ``functor_evaluator.h``.

Example: the built-in LJ evaluator
-----------------------------------

.. code-block:: c++

   struct EvaluatorLJCut {
     struct Coeff { double epsilon, sigma, cut; };
     struct Param { double lj1, lj2, lj3, lj4, offset, cutsq; };
     struct Global {};    // no style-global parameters

     static constexpr bool needs_charge = false;
     static constexpr bool has_mixing = true;
     static constexpr bool has_vdw = true;

     template <bool EFLAG>
     static PairContribution pair(double rsq, const Param &p, double factor_lj) {
       const double r2inv = 1.0 / rsq;
       const double r6inv = r2inv * r2inv * r2inv;
       const double forcelj = r6inv * (p.lj1 * r6inv - p.lj2);
       PairContribution out;
       out.fpair = factor_lj * forcelj * r2inv;
       if constexpr (EFLAG)
         out.energy = factor_lj * (r6inv * (p.lj3 * r6inv - p.lj4) - p.offset);
       else
         out.energy = 0.0;
       return out;
     }

     static int settings(int narg, char **arg, LAMMPS *lmp, double &cut_global, Global &);
     static Coeff parse(int narg, char **arg, LAMMPS *lmp, double cut_global, int &nconsumed);
     static Coeff mix(const Coeff &i, const Coeff &j, Pair *p);
     static Param derive(const Coeff &c, int offset_flag, const Global &);
   };

Registering the style
----------------------

Add a thin class that selects the evaluator and a Coulomb policy.  The
``PairStyle`` macro must appear in the header so the build system can generate
``style_pair.h``:

.. code-block:: c++

   // pair_lj_cut_functor.h
   #ifdef PAIR_CLASS
   // clang-format off
   PairStyle(lj/cut/functor,PairLJCutFunctor);
   // clang-format on
   #else
   #ifndef LMP_PAIR_LJ_CUT_FUNCTOR_H
   #define LMP_PAIR_LJ_CUT_FUNCTOR_H
   #include "evaluator_lj_cut.h"
   #include "functor_coul_policies.h"
   #include "pair_functor.h"
   namespace LAMMPS_NS {
   class PairLJCutFunctor : public PairFunctor<functor::EvaluatorLJCut, functor::CoulNone> {
    public:
     PairLJCutFunctor(class LAMMPS *);
   };
   }    // namespace LAMMPS_NS
   #endif
   #endif

The matching ``.cpp`` defines the (out-of-line) constructor, which anchors the
vtable and instantiates the templated driver for this style:

.. code-block:: c++

   #include "pair_lj_cut_functor.h"
   using namespace LAMMPS_NS;
   PairLJCutFunctor::PairLJCutFunctor(LAMMPS *lmp) :
       PairFunctor<functor::EvaluatorLJCut, functor::CoulNone>(lmp) {}

Choosing a Coulomb policy
-------------------------

The second template argument selects electrostatics.  The driver inspects the
policy's ``constexpr`` flags with ``if constexpr``, so the entire Coulomb code
path is removed from the compiled kernel when ``has_coul`` is false.

.. list-table::
   :header-rows: 1

   * - Policy
     - Use for
     - Status
   * - ``CoulNone``
     - pure van der Waals styles (``lj/cut``, ``morse``, ...)
     - available
   * - ``CoulCut``
     - cutoff Coulomb (``coul/cut``, ``.../coul/cut``)
     - available
   * - ``CoulLong``
     - Ewald/PPPM real space (``coul/long``, ``.../coul/long``)
     - available

TIP4P variants use a dedicated base ``PairFunctorTIP4P<Evaluator>`` instead of a
policy, because the virtual M-site changes the structure of the neighbor loop;
it composes the evaluator (for the van der Waals term) with a ``CoulLong`` member
(for the real-space Coulomb math and tables).  See
``src/FUNCTOR/pair_lj_cut_tip4p_long_functor.h``.

Avoiding a combinatorial explosion of styles
---------------------------------------------

Only *common* combinations of a potential and a Coulomb policy are registered as
fused styles.  For a rare combination, compose a van der Waals functor with a
pure Coulomb functor through :doc:`pair_style hybrid/overlay <pair_hybrid>`.
This is correct but uses a second neighbor list, so prefer a fused style for hot
production combinations.

Testing your style
-------------------

Validate against the original style with the force-styles regression harness
(see :doc:`Developer_unittest`).  Copy the original style's YAML reference (for
example ``unittest/force-styles/tests/mol-pair-lj_cut.yaml``) to a
``..._functor.yaml`` file, change the ``pair_style:`` and ``prerequisites:``
lines to your functor name, and keep the reference numbers.  Because the
optimizations reorder floating-point sums, results match to within the file's
``epsilon`` tolerance rather than necessarily bit-for-bit.  Then run
``ctest -R functor``.

Checklist for a new style
-------------------------

#. Add the ``EvaluatorXxx`` struct in its own ``evaluator_xxx.h`` header.
#. Add the thin ``pair_xxx_functor.h`` / ``.cpp`` with the ``PairStyle`` macro.
#. Write ``doc/src/pair_xxx_functor.rst`` and add the style to
   ``doc/src/Commands_pair.rst`` (alphabetical, no commas).
#. Add a ``..._functor.yaml`` regression test and verify with ``ctest``.
#. Run ``make check`` in ``src`` and ``make style_check`` in ``doc``.
